# CMS member contributions and Q&A first release

The user approved extending the CMS in the DedeCMS-style direction: common membership/contribution/moderation followed by a separate Q&A module. This delivery includes functional member submission, questions, answers, my submissions, administrator moderation and author acceptance. Points, voting, rewards, notifications, anonymous posting and search-engine-rendered Q&A pages are later work.

## Product decisions

- Reuse existing `/api/v3/auth` opaque member tokens (MarketTokenService), not administrator cookies or the separate v2 JWT API.
- Public/member interaction pages live in the existing Vue portal: `/#/web/community` (submissions and mine), `/#/web/questions` (questions and details). The portal can select an active CMS site/language. This first release uses portal hash routes; CMS navigation can link to the portal's full URL. No claim that CMS SSR domains automatically host the portal.
- CMS common site setting `member_content` has enabled=false and model_codes=[] defaults. An administrator explicitly enables it per site. Public readers can browse approved Q&A while submission disabling blocks new writes. Only active members can contribute. Global membership is reused across sites; there is no new site-enrollment model.
- Every question/answer/content submission is pending initially. Member fields cannot control owner, status, reviewer, accepted answer or published route.
- Pending/rejected submissions may be withdrawn by their owner. Published entries require moderator hide. Editing and reputation features are deferred.
- First release content contributions allow scalar-only models (text, textarea, number, boolean, select). Models containing image/file/gallery fields are excluded even when optional, because core attachment IDs do not establish member ownership. No member attachment upload in this release. The administrator UI explains this eligibility limit; safe scalar field schemas are included in context. Revalidate eligibility against the current model version on submit.
- Root is implementing frontend integration and release wiring; two implementation agents own isolated backend domains with the shared interface below. Preserve concurrent CMS/editor/marketplace work. Do not commit/push, mutate customer records or run production migrations during tests.

## Shared CMS backend interface (Task 1)

Namespace `app\cms\service`, plugin source `admin/plugins/cms/app/cms/service/`.

- `ContributionSchema::tables():array`, `install():void`, `mysql():string`. New table `cms_member_submission`: id, site_id, locale, member_id, kind(content/question/answer), parent_id nullable, title, body_html, data JSON, result JSON, request_key, payload_hash, status, lock_version, reviewer_admin_id nullable, review_reason, reviewed_at nullable, created_at, updated_at. Unique(site_id,member_id,request_key); pending/public/owner indexes. Prefix safe; use existing Schema pattern to export 003_member_contributions.sql. No changes to already-shipped migrations.
- `ContributionPolicy::read(string $site):array` returns `{enabled:bool,model_codes:string[],models:[{code,name}]}` from site settings and active site models. `save(string $site,string $actor,array $input):array` uses `cms:site:edit`, site lock, validates enabled bool and model allowlist. `context():array` returns `{sites:[{id,name,default_locale,locales:[{locale,name}],enabled,models:[{code,name}]}],ready:bool}` for active sites only, no private settings/permissions/domains.
- `ContributionService::submit(string $site,string $locale,string $member,string $kind,array $input,?string $parent=null):array`. Allowed payload request_key (8..64 alnum/_/-), title, body_html, model_code, data. Derive member via API auth, validate active member/site/locale/policy. Sanitize HTML, title<=255, body<=40000, body required except optional content body when valid model fields present. content model must be allowed and active; validate via current model version and store server-derived model/version/fields in data. question requires nonempty title/body; answer requires body and published question parent in same site/locale. Kind/parent passed by trusted controller/service. Required request_key yields idempotent retry for identical payload; conflicting payload returns409. Bound per-member/site submission rate using DB recent rows (e.g. 10/minute). Return normalized IDs as strings, lock_version int, data/result decoded.
- `get(string $site,string $id):array` internal full record; `mine(string $site,string $locale,string $member,int $page=1):array`, `listing(string $site,string $locale,string $kind='content',string $status='pending',int $page=1):array` return `{items,total,page,limit}` with limit20.
- `withdraw(string $site,string $member,string $id,int $version):array`: owned pending/rejected only, optimistic version, withdrawn state.
- `review(string $site,string $actor,string $id,int $version,string $decision,string $reason='',?callable $publisher=null):array`: site `cms:submission:review`, transition pending->published/rejected, published->hidden, reject/hide reason required (<=1000); serialize on site lock and compare version. Publisher receives submission and returns result array, called in same transaction only on publish. `reviewContent(...)` additionally asserts cms:content:create and cms:content:publish, creates/publishes ContentService revision with route `/community/articles/{submissionId}`, stores result identifiers/url. Never mix member IDs into admin actor columns.
- `MemberEndpoint` shared base controller extends existing BaseController, methods `member():string` validates MarketTokenService opaque bearer; `input():array`; `action(callable):Response` consistent code=200/data envelope, 401/403/404/409/422/429 handling, no-cache/private, no exception details on500.
- `app\cms\controller\MemberContent` routes `/cms/member/context` GET public; `/cms/member/submissions` GET owned, POST content; `/cms/member/submissions/{id}/withdraw` POST owned. Payload site_id/locale/request_key, member identity never from input.
- `app\admin\plugins\cms\controller\Contributions` extends existing CMS Base: `/admin/plugin/cms/contributions` GET pending content, `/review` POST reviewContent, `/settings` GET policy, `/settings/save` POST policy. GET settings uses cms:site:detail; save cms:site:edit. Review attributes cms:submission:review, list cms:submission:list. Add Contribution group to PermissionCatalog (list/review, ceilings identity). Existing roles do not silently gain new persisted permissions. Root updates manifest/menu/frontend and mirrors source.

## Q&A backend interface (Task 2)

New plugin `admin/plugins/qa`, requires cms>=1.3.0. Source app/qa/service/QuestionService.php and Schema.php, app/qa/controller/Questions.php, app/admin/plugins/qa/controller/Moderation.php. Root owns plugin.json, Plugin.php, frontend and final publication; backend agent creates SQL migration001 from Schema.

- `Schema::tables/install/mysql` creates `qa_question`: id primary = shared question submission ID; site_id, locale, accepted_answer_id nullable, closed bool, lock_version int, timestamps. Shared cms_member_submission stores answers and question body, ownership/review status.
- `QuestionService::ask($site,$locale,$member,array $input):array` calls common submit(kind question), inserts qa_question idempotently in same site-locked transaction. Returns shared record plus accepted_answer_id, closed and question_version.
- `answer($site,$locale,$member,$question,array $input):array` requires published, same-site/locale, open question, then common submit(kind answer,parent question).
- `listing($site,$locale,string $q='',int $page=1):array` and `detail($site,$locale,$id):array` expose published questions/answers only (select safe fields, no reviewer/reason/request key/hash/member contact data). Return question `id,title,body_html,member_id,author_name,status,lock_version,question_version,accepted_answer_id,closed,created_at` and detail answers list (bounded100, include total if truncated). Site active and locale enabled even for reads. Pending details only available through common owned mine/admin list, never public.
- `accept($site,$locale,$member,$question,$answer,int $questionVersion):array`: question owner only, both published and same parent/site/locale; lock site/question, CAS question_version; accept single answer, mark closed, increment version. No self-auth spoofing. `setClosed(...)` optional later, not required.
- `review($site,$actor,$submission,$version,$decision,$reason=''):array` ensures kind question/answer, calls common review. Hiding an accepted answer clears acceptance and reopens question atomically; hiding a question hides it and its replies from public queries. QA admin route also requires qa:moderation:review; common CMS site submission permission remains the site boundary.
- Public/member controller `/qa/api/context` GET can delegate ContributionPolicy.context, `/qa/api/questions` GET public, POST ask; `/qa/api/questions/{id}` GET public; `/answers` POST; `/accept` POST. MemberEndpoint base for opaque bearer and envelopes. Guard plugin by app/qa controller ownership; default global PluginApplicationGuard preserves activation and cms dependency. Add explicit write rate handling through common service.
- Admin controller extends AdminApiController: `/admin/plugin/qa/moderation` GET uses cms site submission:list and lists kind question/answer, filters valid status; `/review` POST delegates QuestionService.review and plugin permission. Auth/CSRF via existing admin base, actor only request context. Return envelope consistent with CMS.

## Frontend and wiring (root)

- Add member policy UI in CMS site settings, common contributions admin menu/page, qa moderation page/manifest. Common APIs published according to current frontend plugin layout.
- Public portal uses opaque memberSession and axios separate from admin cookie client. Community page model selector + member content form + owned list/withdraw. Q&A page public list/detail, login CTA, ask/answer forms, accept button only apparent owner but backend authoritative. Reload latest details/version after actions. Errors and empty/pending states explicit. Never v-html untrusted input; only server-sanitized published body may be rendered.
- Profile links to Community/Questions and new public static routes. Plugin inactivity yields clear unavailable state, not unauthorized fallback.
- Backend tests isolate SQLite/member fixtures, CAS/state/site/locale/actor invariants, bearer behavior and actual route metadata. Frontend tests cover query/ID/context, pending feedback, owner affordances and error handling; run typechecks/build and independent security/domain review.
- Deployment readiness: CMS version1.3.0 adds one append-only migration and two declared capabilities; QA1.0.0 installation requires this CMS version. Do not silently enable site participation, grant roles or fake plugin activation. Installation/upgrade steps will be concrete and tested before any real deployment decision.
