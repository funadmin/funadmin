# 插件复数路由与显式覆盖设计

## 意图

插件源码目录和安装目录继续使用 `plugins/{code}` 作为隔离边界；插件拥有的后台页面和接口统一改为复数命名空间 `/plugins/{code}/...`，让 URL 与目录概念一致。需要替换宿主行为时，使用清单声明的显式路由覆盖，不允许插件通过把文件写入宿主目录来覆盖核心类。

## 目标

- 新插件清单、脚手架、文档和内置插件统一使用 `/admin/plugins/{code}/...` 与 `/#/admin/plugins/{code}/...`。
- 只接受 `/admin/plugins/{code}/...` 和 `/#/admin/plugins/{code}/...`，不保留单数路由兼容层。
- 插件包和安装运行目录保持 `admin/plugins/{code}`、`admin/app/admin/plugins/{code}`。
- 插件可以声明受控的 `routeOverrides`，替换指定宿主路由；目标重复、插件未启用、目标不存在或处理器不属于当前插件时拒绝加载。
- 卸载、升级和回滚继续按插件资源登记表处理，不删除宿主文件。

## 非目标

- 不允许插件直接写入 `admin/app/admin/controller`、`admin/app/common` 或其他宿主目录。
- 不修改独立应用插件现有的 `/{code}/...` 路由。
- 不把所有 `/plugins/...` 资源路径改成同一套语义；公共钩子和静态资源继续使用各自的聚合路径。

## 约束

- Webman 路由注册遇到同一方法和路径会抛出冲突异常，覆盖路由必须先移除被覆盖定义再注册。
- Composer 的 `app\\` PSR-4 映射要求每个完全限定类名只有一个实现；覆盖通过路由回调选择实现，不通过重复类名。
- 插件路由必须经过激活检查；覆盖处理器只能位于当前插件的 `app\\admin\\plugins\\{code}\\controller` 命名空间。

## 方案

### 方案 A：只改 URL

把所有插件 URL 改成复数，保留目录和命名空间隔离。实现成本低、兼容性最好，但不能提供核心路由替换能力。

### 方案 B：复数 URL + 显式路由覆盖（采用）

在方案 A 的基础上增加 `routeOverrides`。清单只声明目标路径、HTTP 方法、处理器和优先级；加载器校验目标和处理器归属，并在同一批路由定义中替换目标。

### 方案 C：去掉 `plugins` 目录并允许直接覆盖

插件发布到宿主业务目录，依靠同名文件覆盖核心实现。该方案会破坏 Composer 类唯一性、插件卸载归属、升级回滚和多插件冲突检查，因此不采用。

## 清单接口

```json
{
  "routeOverrides": [
    {
      "methods": ["GET"],
      "path": "/admin/system/user/profile",
      "controller": "app\\admin\\plugins\\demo\\controller\\ProfileOverride",
      "action": "show",
      "priority": 100
    }
  ]
}
```

`methods`、`path`、`controller`、`action` 必填，`priority` 默认为 100。覆盖项不允许声明插件自身命名空间路径；覆盖目标必须已经存在于核心或已启用插件路由中。当前版本只允许替换路由回调，不改变原路径的中间件链和 HTTP 方法。

## 路由行为

- `plugin.json` 的路径固定为 `/plugins/{code}/...`。
- Webman 注解路由加载器只注册复数路径。
- 前端动态路由只挂载复数路径。
- 插件守卫和路由 DTO 校验只识别复数前缀。

## 验收

- 内置 CMS、文档、OSS、QA 和示例插件均可通过复数前端 URL 和复数 API 访问。
- 单数路径不会被注册或跳转。
- 停用插件后复数和单数 URL 都被阻断。
- 合法覆盖替换目标回调；重复覆盖、越界处理器、未注册目标和停用插件覆盖均被拒绝。
- 插件卸载不会删除或修改宿主控制器文件。
