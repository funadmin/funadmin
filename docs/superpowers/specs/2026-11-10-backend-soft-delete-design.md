# 后台数据全部软删除设计

## 目标与原因

后台所有数据删除时只做标记，不物理删除，便于追溯和恢复。现状不统一：66 张核心表里有 46 张有 `deleted_at` 列，但约 15 个对应模型没有启用软删除（如 `Admin`），于是代码里散落着手写的 `whereNull('deleted_at')`，且 `$admin->delete()` 实际是物理删除；另有约 20 张表没有 `deleted_at` 列。

用户决定：
- 全部表都软删除，没有 `deleted_at` 的表补上。
- 唯一索引冲突用“删除标记列”解决。
- 日志页面（前台管理界面）增加“真实删除”。

## 范围

### 包含

- 核心库全部表（`admin/database/core/migrations` 中的 `fun_*` 表）及其模型（`app/admin`、`app/common`、`app/api` 下的 Eloquent 模型）。
- 操作日志页面的彻底删除。

### 不包含（后续单独处理）

- 插件自己的表（CMS、文档、问答、OSS）。CMS 正由另一个会话改为 Eloquent 模型，等它完成后按同样规则跟进。
- 代码生成器生成的业务表的建表模板（生成器由另一个会话维护）。本次只保证已生成模型使用的软删除 trait 行为兼容。

## 设计

### 1. 表结构（新核心迁移 005）

每张核心表：
- 补 `deleted_at DATETIME NULL` 及索引（已有的跳过）。
- 新增 `deleted_token BIGINT UNSIGNED NOT NULL DEFAULT 0`。0 表示未删除；软删除时写入该行 `id`。
- 每个 `UNIQUE KEY`（主键除外）重建为“原列 + `deleted_token`”。未删除行之间唯一性照旧由数据库保证；已删除行的 `deleted_token` 各不相同，不再占用唯一值，删除后可以用相同的用户名、菜单路径、权限码、插件编码、Casbin 规则等重新创建。

迁移照现有约定提供 SQL（`database/core/migrations/005_soft_delete.sql`，核心权威源）和等价 PHP（`database/migrations/005_soft_delete.php`），全部语句可重复执行。

### 2. 软删除行为（`app\common\model\concern\LaravelSoftDelete`）

- 单条删除（`$model->delete()`）：写 `deleted_at = now`、`deleted_token = id`。
- 批量删除（`Model::where(...)->delete()`）：同样写这两列（`deleted_token` 取各行自身 `id`）。
- 恢复（`restore()`，单条和批量）：`deleted_at = null`、`deleted_token = 0`。
- 恢复时如果和现有未删除记录撞了唯一值（例如删了 `zhangsan` 又新建了一个 `zhangsan`，再去恢复旧的），数据库会拒绝。系统把这种情况统一转成明确的业务错误："已存在相同的记录，无法恢复，请先修改或删除现有记录"。两条记录都保持原样，不做自动合并或改名。
- 真实删除用 `forceDelete()`。
- 表上没有 `deleted_token` 列时只写 `deleted_at`（按表缓存列检测）。这样插件表和测试里自建的简化表不受影响。
- 查询自动排除已删除行（Eloquent 标准行为），需要包含已删除时用 `withTrashed()` / `onlyTrashed()`。

### 3. 模型与查询

- 核心表对应的所有模型都使用 `LaravelSoftDelete`。
- 删掉模型查询上手写的 `whereNull('deleted_at')`，因为 trait 已经覆盖。
- 查询构造器直查（`Db::table`）、`join` 进来的表、原生 SQL 不经过模型，要显式加 `deleted_at IS NULL`，删除要改成写这两列。
- Casbin 适配器（`DatabaseAdapter`）走 `CasbinRule` 模型，自动适用。

### 4. 基础设施类表

会话、令牌、登录尝试、nonce、队列、迁移记录、事件和发件箱等表，也按用户要求软删除。这些表原来的过期清理改为只做软删除标记。如果某张表由第三方库直接物理删除，就只补列，并在报告中列出。

已软删除的记录一律保留。用户明确要求不做任何自动删除，也不做定期清理。真实删除只能由管理员在回收站中手动执行，例如操作日志的"彻底删除"和会员回收站已有的彻底删除。

### 5. 操作日志真实删除

- 后端 `SystemOperationLog` 新增：
  - 列表参数 `trashed=1`：只看已删除的日志（回收站）。
  - `DELETE /admin/system/log/operation/force`：按 `ids` 真实删除回收站中的日志；未删除的日志必须先删除（进入回收站）才能彻底删除。
  - `DELETE /admin/system/log/operation/clear-force`：清空回收站：真实删除当前数据范围内已软删除的日志，不碰未删除的日志（用户规则：真实删除只能在回收站进行）。
- 新方法按现有约定得到各自的推导权限码，并登记到权限和鉴权快照。
- 前端 `operation.vue`：
  - 保留“删除”“清空”，它们是软删除。
  - 新增“彻底删除”（选中项）和“回收站”开关。
  - 回收站里提供“彻底删除”和“清空回收站”。
  - 真实删除都要二次确认，提示不可恢复。
  - 新文字中英文齐全。

### 6. 会员（`fun_member`）：注销冷静期

会员删除后可能要找回账号。如果用户名、手机号、邮箱在删除后立刻释放，别人就能注册占用，原主人再也恢复不了。用户确认按推荐做，规则如下。

**冷静期**
- 时长由 `config/soft_delete.php` 的 `member_cooling_days` 配置，默认 30 天。这个配置文件由第 8 个任务新建。
- 冷静期内，被删会员的用户名、手机号、邮箱仍然保留：注册和后台新建、编辑会员时，唯一性检查要连同"冷静期内的已删除会员"一起查。冲突时提示该账号已注销，可在冷静期内找回。
- 冷静期过后这些值放开，可以用来注册新账号。旧账号仍保留为软删除。

**找回**
- 本次只做管理员在后台回收站恢复，复用现有的 `SystemMember::recycle/restore`。会员自助找回以后再做。
- 恢复时撞上同号新账号，返回统一的冲突提示（第 2 节）。

**连带处理**
- 删除会员：接口会话（`member_api_session`）、分组和标签关联一起软删除。已登录的设备立即失效。
- 恢复会员：分组和标签关联一起恢复。会话不恢复，需要重新登录。

**空值**
- 用户名、手机号、邮箱选填时一律存 NULL，不存空字符串。否则多个空字符串会在唯一索引上互相冲突。

**被引用的数据**
- 会员等级、分组、标签还被未删除会员使用时，不允许删除。原因是软删除后外键 `fk_member_level` 拦不住，会员会挂在已删除的等级上。

**保留**
- 已删除会员的数据一直保留，只有管理员在会员回收站手动彻底删除时才会真正删除。

**索引**
- 迁移 005 顺便删掉与唯一索引首列重复的普通索引：`username`、`mobile`、`email`。

### 7. 测试

- 迁移：SQLite 与 MySQL 下执行 005 后，每张表都有两列，唯一索引都含 `deleted_token`，重复执行无错。
- trait：删除后用相同唯一值重建成功；未删除行重复仍被拒绝；批量删除和恢复正确写两列；没有 `deleted_token` 的表正常工作。
- 回归：管理员删除后不能登录，同名可重建；插件停用再启用时菜单和权限能重新登记；Casbin 规则删除后能重新添加。
- 日志：软删除、回收站、彻底删除、彻底清空的接口和权限；前端组件测试。
- 现有测试里自建的简化表，凡对应模型新增了软删除的，都补上 `deleted_at` 列。
